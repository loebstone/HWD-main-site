# HWD Main Site

The private HWD Farm family website with suite sign-in, secure grouped documents, announcements, family-time rotation, shared navigation, Contact and seasonal dues instructions.

## Run & operate

- Start API: `pnpm --filter @workspace/api-server run dev` (workflow: **API Server**).
- Start site: `pnpm --filter @workspace/hwd-main-site run dev` (workflow: **web**).
- Typecheck: `pnpm run typecheck`; build: `pnpm run build`.
- Regenerate API hooks and Zod schemas: `pnpm --filter @workspace/api-spec run codegen`.
- Apply Drizzle schema in development only: `pnpm --filter @workspace/db run push`.
- Append-only audit and no-hard-delete protections install idempotently when the API starts. The manual `security:dev` command is for development only.
- After an additive schema push, API startup runs the recorded, transactional document-group backfill before listening. `group_id` remains nullable so schema validation can precede that backfill safely on populated databases.
- Automated security and browser suite: `pnpm --filter @workspace/api-server test`. Browser walk-through also needs Playwright Chromium.
- Tests use an isolated, randomly named schema in the development database and synthetic identities only.
- Before any reporting query, state the environment and confirm the database host. Never write to production.

## Required secrets and settings

- `DATABASE_URL` — Replit PostgreSQL connection.
- `SESSION_SECRET` — session, token, and rate-limit hashing.
- `SITE_SERVICE_KEY` — bearer credential for HWD Roster service calls and the Scheduler rotation service.
- `ROSTER_BASE_URL` — HWD Roster origin.
- `SCHEDULER_BASE_URL` — Scheduler origin for server-side rotation lookups. Development: the Scheduler's development origin, supplied by Peter; production: `https://calendar.hwdfarm.com`. Never substitute the production Scheduler for an unset development value. Missing/unreachable configuration omits only the family-time bar. Do not set production settings from Agent.
- `MAIL_FROM` — sender address.
- `BOOTSTRAP_PERSON_ID` — Roster person id eligible for the one-time first-admin grant.
- `APP_ORIGIN` — explicit public origin in production; development may derive `https://$REPLIT_DEV_DOMAIN`.
- `TRUSTED_PROXY_HOPS` — optional startup setting, integer 0–8: number of forwarding hops Replit adds in front of the app in this environment; set from the production diagnostic line, never guessed. Unset/invalid falls back to the audited development depth 3 with a startup log explaining why. Changing it requires a process restart, not a rebuild.
- Resend is called through the connected Replit integration using `@replit/connectors-sdk`; there is no separate `RESEND_API_KEY` app variable.
- Private App Storage uses the Replit-provided bucket configuration (`DEFAULT_OBJECT_STORAGE_BUCKET_ID`, `PRIVATE_OBJECT_DIR`, and `PUBLIC_OBJECT_SEARCH_PATHS` as applicable); do not make document objects public.
- Missing optional Roster, mail, bootstrap, or origin configuration disables only the feature that needs it, with a clear server log. It does not block build/startup. Never invent a fallback identity, send development mail, or derive a production origin.

## Stack

- pnpm workspace, Node.js 24, TypeScript; Express 5 API.
- React, Vite, Tailwind, shadcn/ui.
- PostgreSQL and Drizzle ORM; Zod validation; OpenAPI contract and generated Orval hooks.
- Private file objects in Replit App Storage; never expose bucket URLs or signed public links.

## Architecture and security decisions

- **Proxy depth:** Express uses the numeric `TRUSTED_PROXY_HOPS` startup setting (0–8; explained fallback 3), counting from the socket/right-hand end, never `true` or the leftmost forwarded value. A development ingress audit on 2026-10-28 observed `visitor, ingress proxy, loopback router` in X-Forwarded-For with a loopback socket; depth 1 incorrectly selected loopback. The chain was stable across ordinary requests and requests supplying one/multiple spoofed XFF entries, which Replit stripped upstream. Depth 3 selects the edge-presented visitor on that development ingress. Production depth must be set from its diagnostic evidence, not assumed from development; re-audit after routing changes and account for shorter alternate ingress paths.
- **Production evidence:** The API build embeds a fixed identifier in the format `<UTC ISO timestamp>-<8 random hex characters>`. Startup logs it once, and `GET /api/healthz` returns `{status, build}` so the served build can be matched to startup logs. Source-mode tests use the explicit identifier `source-unbundled`. Startup also logs the effective proxy depth, source, and reason. Each `GET /api/auth/verify` logs `forwardedFor`, `socketAddress`, `resolvedIp`, and `trustedProxyHops` before rate limiting, including refused requests; it never logs cookies, query strings, tokens, or request bodies. Use these lines after republishing to distinguish stale builds from an incorrect production forwarding depth.
- Auth rate limits remain PostgreSQL-backed. Throttled link requests log the IP/email throttle flags (no email or token), while returning the same neutral body. Oversized JSON returns 413 with a plain size-limit message.
- Legacy `/api/admin/apps` URLs retain the HTTPS Farm-host rule for compatibility; these old settings no longer drive navigation. Suite menu URLs use the validation policy below. Credentials and suffix/lookalike hosts are refused with a clear validation message.

- Roster is authoritative; the site stores no independent member directory. Sign-in tokens and session cookies are random bearer secrets whose database representation is SHA-256 hashed.
- Email is neutral for allowed and refused addresses. Development sign-in links go only to server logs; production delivery uses the connected Resend integration. The continue page checks the token without consuming it; only the Continue action attempts the atomic single-use consume.
- All API routes require a valid session except the explicit anonymous list below. Roles are checked on the server for every protected operation.
- **View as member:** `POST /api/auth/view-as-member` accepts `{enabled:boolean}` and is session-protected/CSRF-protected. It locks the session row and rechecks the underlying admin role (Roster role for SSO, active local admin grant for the back door). The sole role-change column is `site_sessions.view_as_member boolean NOT NULL DEFAULT false`, safe for populated tables. While enabled the effective identity for every private route is member with apps `site,scheduler,roster`; all editor/admin operations refuse, staff groups/documents return 404, and tools/cards are omitted. Switching back is the narrowly authorized exception, using the actual admin identity for this same session; grants/Roster roles/apps are never overwritten. Repeated identical requests do not duplicate audit transitions. Audit actions: `view-as-member-on`, `view-as-member-off`.
- **Roster SSO contract:** before mounting React on a protected-page visit, the client checks the site session; on 401 it fetches `GET /api/auth/roster-entry?to=<path>` and immediately replaces the browser location with `{ROSTER_BASE_URL}/sign-in?app=site&to=<encoded path>&origin=<encoded APP_ORIGIN>`. No intermediate button page or private shell renders. Intended path/query/fragment are preserved. `/sign-in` is for direct visits only: “Sign in to HWD Farm” and one “Sign in” button. Member sign-in/sign-out copy never mentions the Roster. Paths must start with a single `/`; full URLs, `//`, backslashes, encoded separator tricks and control characters are refused. Default is `/`.
- Roster returns the browser to `GET /auth/sso?ticket=<raw>&to=<path>` (explicitly routed to the API service, not Vite). The server POSTs `{ticket}` to `{ROSTER_BASE_URL}/api/service/sso-redeem` using `SITE_SERVICE_KEY`, a 10-second timeout and no redirects. Roster owns atomic 60-second/single-use ticket enforcement. A 401, outage, malformed answer or redirect refuses sign-in without fallback. This callback is DB-rate-limited to 20 requests per 15 minutes per visitor address.
- **Role rule:** sessions with `sign_in_method = roster` use only the validated `role` from redemption, stored as `roster_role`; neither `rosterAdmin` nor local grants override it. `authenticated_at` records the Roster timestamp. Daily `sign-in-check` rechecks eligibility and refreshes the validated `apps` array, not role. Local grants remain the sole role source for `magic-link`/legacy sessions. SSO never bootstraps or creates local grants.
- Both Roster contracts accept optional `apps` and `grants`. Only `apps` is persisted (`roster_apps` JSONB), at sign-in and each successful eligibility recheck; no local copy of Roster grants/member directory is maintained. `apps = []` explicitly means no tools, including for admins. Only NULL/missing legacy lists fall back to admin-only tools. IDs `forecast` and `captable` are recognized (`cap-table` is a compatibility alias). Outage grace preserves the last successful list; a refused eligibility answer still ends the session.
- **Admin back door:** the old email form lives only at `/admin/sign-in`, unlinked from site navigation; local active admins (or the eligible never-before-granted bootstrap admin) can complete it. Member tokens cannot create back-door sessions. Existing neutral responses, atomic token consume, console-only development email, Roster eligibility recheck, rate limits and cookie protections remain. It does not bypass Roster eligibility/network checks: if the Roster service itself is unreachable, new back-door sign-ins still fail closed.
- Both methods use the same session table/cookie, 30-day sliding window, 12-month maximum and daily eligibility checks. Existing rows default to `magic-link`; their historical authentication timestamp may be NULL. Site sign-out deletes only the site session, then offers a separate link to `{ROSTER_BASE_URL}/sign-out` labeled “Sign out of all Farm apps”.
- Document downloads are authenticated streams with `Cache-Control: no-store`; private object keys never reach the client. PDF uploads are signature-checked and capped at 50 MB.
- Documents, grants, and announcements are retired/ended, not deleted. Sign-out is the requested exception and removes that session row.
- Audit rows are protected by database triggers against UPDATE, DELETE, and TRUNCATE, and public mutation grants are revoked. On API startup, the application idempotently creates missing functions/triggers in every environment; it never drops/recreates them or changes existing rows. `lib/db/security.sql` is the readable source at the repository root. The API build copies that source to `artifacts/api-server/dist/security.sql`; the bundled startup installer reads the adjacent copy, so deployment does not depend on retaining the source tree. Source-mode tests fall back to the readable source. `security:dev` is a local development-only installer.
- `site_session` is the only site cookie; its 30-day sliding expiry has a 12-month absolute limit. Daily Roster checks retry one time only on network/timeout/server unavailability (5 seconds, then 8 seconds); a continued outage is throttled for an hour and tolerated for up to three days since the last successful check. A real not-allowed answer ends the session immediately.
- **Database separation:** each Replit app has its own PostgreSQL instance, even though the default database name is `heliumdb`. This site's `heliumdb` is a separate instance from the Roster's database. The development query returned `current_database() = heliumdb`; `inet_server_addr()` returned `NULL` because this connection uses a local socket. The configured instance host is `helium`.

## Suite menu and Contact

- Member navigation defaults, in order: **Home · Announcements · Scheduler · Family Directory · Documents · Contact**, then permitted **Tools**, then **Admin** for editors/admins. Scheduler and Family Directory use `https://calendar.hwdfarm.com` and `https://roster.hwdfarm.com`. Tools link to Forecast/Cap Table only when the session apps list permits them (legacy admin-only fallback above). External navigation stays in the same tab. Document Open/Photo Archive actions are unchanged and keep new tabs.
- Header/Home link and sign-in use the same eight-conifer inline SVG treeline, with the HWD Farm wordmark. Home keeps featured document-group Quick access, Reminders, notice and Recent; the former Farm apps strip is removed.
- Public **GET `/api/suite/menu`** returns exactly `{ version: number, logoSvg: string, items: [{ id, label, href, order }], tools: [{ id, label, href }], signOutHref: string }`. It is identical for anonymous/member/admin requests, ignores cookies, sets none, and contains only public links/static SVG. `version` is an integer settings revision (defaults to 1; increments on saves); consumers should not interpret it as a person's permissions.
- Consumers fetch without credentials, allow this site's origin in their own CSP `connect-src`, sort `items` by `order`, and independently filter Tools using their own authenticated apps identity. Item IDs are `home, announcements, scheduler, directory, documents, contact`; tool IDs are `forecast, captable`. Home/Announcements/Documents/Contact defaults use this site's configured `APP_ORIGIN`; `signOutHref` is the authority's `/sign-out`.
- Cache is **`public, max-age=300`**, with `Vary: Origin`. CORS permits GET from HTTPS `hwdfarm.com`/subdomains and **only exact Replit origins registered by the current menu links, APP_ORIGIN, or ROSTER_BASE_URL**. It never allows arbitrary `*.replit.app`/`*.replit.dev` tenants or credentials. OPTIONS is solely a GET preflight; other methods return 405 and unknown subpaths fall through to normal authentication.
- Admin-only **GET/PUT `/api/admin/suite-menu`**, page `/admin/suite-menu`, edits fixed item/tool IDs' labels and HTTPS hrefs, plus unique menu order. Allowed hosts: `hwdfarm.com`/subdomains, and app/development hosts ending `.replit.app` or `.replit.dev` (not their bare platform domains); no URL credentials. Replit origins support development/staging and the existing Replit-published site. Saves persist versioned `suite-menu` settings and audit **menu-edit**, transactionally. `/admin/apps` now redirects to Suite menu; old settings/compatibility API are retained, not deleted.
- Signed-in `/contact` uses **GET `/api/contact`** returning only `{configured:boolean}`; no recipient is exposed to members. When unset it says **“Contact isn't set up yet”**, no form is shown, and POST is refused with 409. The Contact menu link remains.
- Admin-only `/admin/contact`, **GET/PUT `/api/admin/contact`**, stores `contact.recipient` in site settings; the label is **“Contact messages go to:”**. A valid email enables delivery; empty string disables it. Changes audit **contact-settings-edit** without disclosing the address in the description.
- **POST `/api/contact`** accepts subject (trimmed, nonempty, max 200, single line) and message (trimmed, nonempty, max 5000). Name/email come only from the authenticated session. Resend uses existing connected integration, MAIL_FROM, recipient setting, reply-to = safely quoted member full name plus email, and subject prefix `[HWD Farm contact]`; body contains member full name/email and message. No new key/environment setting is needed. Development logs the synthetic/development mail instead of sending.
- Contact quotas are **5 successful sends/person/UTC day and 20/site/UTC day**. A database transaction/advisory lock serializes quota checking, delivery and append-only **contact-send** audit (description = subject only, never message body). All processes share the lock; a failed transport returns 503, records no successful-send audit and consumes no quota. Quota refusals return 429. A transport acceptance followed by database/connection failure cannot guarantee exactly-once external delivery; no automatic retry is attempted.
- Contact/admin mutations retain session/role authorization, CSRF protections, no-store responses and plain error hygiene. All fixtures use isolated synthetic identities and no production delivery.

## Old-site content import

- Admin > Documents has an admin-only **Import from old site** panel. Server routes are `GET/POST /api/admin/old-site-import`; neither is anonymous or editor-accessible.
- `artifacts/api-server/src/lib/old-site-fetch.ts` reads the published CSV fresh on every run, parses quoted CSV, restricts all fetches/redirects to HTTPS Google hosts, limits fetches to 20 seconds and PDFs to 50 MB, and follows at most one Drive confirmation link/form.
- `artifacts/api-server/src/lib/old-site-import.ts` validates/maps each row, continues after individual failures, and uses the same private-storage/document-creation function as manual uploads. No signed/public file URLs are generated. The current published sheet's blank twelfth header is the supporting-text column.
- The importer maps legacy sections to the five seeded group IDs, including after a group is renamed. A retired destination is refused, not silently substituted.
- Importing is idempotent by the original sheet `id`, stored as `legacy_sheet_id` on documents/announcements, including retired records. Per-row database advisory locks and unique indexes prevent concurrent duplicates. Every created row also has an `import` audit entry attributed to the authenticated admin with description `Import from old site: <sheet id>`.
- Runs execute in the background so the HTTP request does not time out. The last run table, time, actor, source hash and progress are persisted as `old-site-import-last-run` in site settings; the UI polls while running. A stale two-minute progress lease reports an interrupted run and permits a safe rerun. Dry runs write the report only, fetch no source files, and label planned rows **would import**.
- The browser panel lives in `artifacts/hwd-main-site/src/components/admin/old-site-import.tsx`; contracts and hooks are generated from the OpenAPI spec.

## Document groups and reversible migration

- The Documents menu replaces the old section menu entries. `/documents` lists visible active groups in sort order; `/documents/:slug` lists live records using `list` or newest-year-first `by_year` layout and client-side search. Scheduler replaces the old Calendar menu label; Announcements and Admin retain their existing behavior.
- The migration runs transactionally under an advisory lock, once per database, recorded as `document-groups` in `site_data_migrations`. It creates Shareholders' meetings, Directors' meetings, Governing docs & policies, Logging, Photo archive, in that order, all visible to everyone. It assigns **all** existing records, including retired records, by their legacy section; any unassigned record or changed total aborts the entire transaction. Subsequent boots never reset moved documents, renamed groups or visibility.
- Migration records contain counts per group and the original document IDs, sections and prior group IDs. Neither document IDs, bytes, storage keys, URLs, upload timestamps, versions nor retirement status are changed. The old section remains migration history, not the current navigation or grouping source; metadata edits and moves preserve it. New manual documents have NULL legacy section rather than an invented classification; imported records retain their mapped legacy section. No migration reads or writes production from the Agent.
- `group_id` remains **permanently nullable**; no live-group CHECK is installed at startup. Publish validates the development schema before the startup data backfill can run, so such a CHECK would reject the existing live documents. Its nullable foreign key prevents dangling non-null IDs. New uploads, edits and moves require an active group at the API boundary. Existing unassigned records remain visible in Admin as “Needs a group” and in staff Recently added, and can be opened/moved by staff; members receive neither their metadata nor access to their contents. Group pages omit them for every role. The old section-dependent year CHECK is removed: legacy import still requires/infers meeting years, while current group-based forms allow an optional year (shown as “Undated”).
- Rollback procedure for an operator, **not executed on production**: stop the new API; retain the schema, groups, immutable migration journal and private objects; revert the app to the section-based version. Existing records remain usable via their unchanged section. If reversing the group assignment itself, use `details.originalAssignments` to restore only those recorded document IDs and prior group IDs; never overwrite records created later, never delete groups/documents/journal/files. The isolated test exercises that restoration inside a rolled-back transaction and checks preserved metadata. Do not erase the journal to force a rerun.
- `tests/populated-schema.test.ts` applies the captured read-only publish diff (`tests/fixtures/document-groups-publish.sql`) to isolated synthetic legacy tables containing 24 live and 6 retired documents plus announcements, grants, sessions, settings and audit rows, then runs startup protections/backfill twice. Only the fixture schema qualifier is adapted for isolation; no production data is copied. When the schema evolves, refresh/re-audit this SQL fixture from the read-only publish diff.
- Staff means editors and admins. Members receive no staff groups, documents, Home counts/recent titles, or featured cards. A member guessing a staff group's slug or a document's open URL receives 404. Staff “Show retired” retains document history even after an empty group is retired. Every document stream still requires a session and is no-store; private keys are never serialized.
- Editors/admins manage groups and documents. Group mutations lock the group; uploads, edits, replacements and bulk moves lock the target group, preventing retirement racing a new live document. A group with live documents cannot be retired; all rows/files are retained. Groups forbid hard delete/TRUNCATE and the migration journal forbids UPDATE/DELETE/TRUNCATE at the database level.
- Audit actions: `group-create`, `group-edit`, `group-retire`, `document-move`, and `home-edit` (featured selection). A metadata edit that changes group also records `document-move`. Bulk moves are atomic and audit each document with old/new group IDs.
- The old `/api/admin/home` featured-group setting is retained for compatibility, but no longer drives visible Home cards. Document groups are reached through Documents; Home no longer renders document Quick access or Recently added.

## Home, family time, slideshow and dues

- Home order is suite header (phone hamburger), illustration, Announcements, optional slideshow, then cards. The Announcements block contains “Latest minutes” for the newest uploaded live document in the original shareholders/directors groups, honoring current group visibility/retirement; the line is omitted when none is visible. The existing Home notice/reminders remain inside this block. The family-time bar is at its bottom.
- `/api/home` adds `latestMinutes`, `slideshowEmbedUrl`, `familyTime` and server-filtered `cards`. Legacy summary/group/recent fields remain for compatibility but the new Home does not render them. Scheduler/Family Directory/Documents/Contact cards are universal; Forecast/Cap Table cards require an explicit matching session app (no legacy-admin fallback for these cards). Dues appears only when its season is open. Farm cards remain same-tab; latest-minutes/document Open remains new-tab.
- **Family-time display decision:** Peter requested a non-personalized bar: only `Family time <year>`, the families in slot order with dates, and the small Scheduler link. No personal lead-in or member-family highlight. Rows are compact on phones and use four columns on wide screens. **Why:** Peter's decision on 2026-11-03.
- The server GETs `{SCHEDULER_BASE_URL}/api/service/rotation?year=YYYY` with the existing `SITE_SERVICE_KEY`, a 10-second timeout, and redirect refusal. Never send email or personId. Only validated year/slots data is returned with schedulerHref; personalized upstream fields are ignored. Successful nonempty answers are cached for one hour; empty/failure/missing-setting answers for five minutes, shared per year/origin, bounded to 1,000 entries per process with in-flight deduplication. TTL begins when the request completes. One outage log per origin/year includes only reason category, requested year, and optional HTTP status; recovery permits the next outage's log. Categories include unreachable, 401, other status, empty slots, setting missing, invalid setting and invalid response. An empty current year or an ended current season tries the next year exactly once; two empty years omit the bar. Transport/auth/validation failures do not trigger a guessed future season. Family rows follow slot order and render every segment; displayed last dates subtract one day because service end dates are exclusive.
- **Scheduler response boundary:** live responses include numeric `familyGroupId` and `generatedFrom`. Accept safe integer or nonempty string family IDs and normalize them to the site's existing string IDs. Accept null displayColor as the existing empty-string/green UI fallback. Accept valid date-only or ISO timestamp dates and retain their calendar-date prefix (never shift a family's day through timezone conversion). Extra upstream fields are ignored; missing required consumed fields, invalid dates/ranges and wrong response years remain errors. **Why:** the Scheduler is the contract authority; its valid numeric IDs previously caused the site's string-only validator to refuse otherwise complete answers. Recorded non-personal 2026/2027 service bodies live in `artifacts/api-server/tests/fixtures/scheduler-rotation-live.json`; regression coverage is in `tests/family-time-contract.test.ts`.
- **Check family time** in Admin > Home calls admin-only `GET /api/admin/family-time/check`, returning exactly `{ok,reason,year,slotCount}` with no-store caching headers. It freshly checks the same non-personalized current/next season; it never reads or overwrites Home's cache. Success displays exactly `OK · Year <year> · <n> slots`. Failures return `ok:false` and the safe reason category, not upstream bodies/errors. Editors, members and admins in member-view mode are refused. No anonymous route was added.
- `GET/PUT /api/admin/home-display` (admin only) stores `home-display.slideshowEmbedUrl`; null/blank removes it. Validation accepts only HTTPS `smugmug.com` or its subdomains, no credentials or nonstandard ports. Home renders no placeholder when unset; otherwise a lazy 16:9 iframe, no delegated permissions, `referrerPolicy=no-referrer`.
- **The one CSP exception** on the HTML-serving Vite development and production-preview hosts is `frame-src 'self' https://*.smugmug.com`, solely for family slideshows. No other directive is relaxed; API and private-PDF CSPs are unchanged. Use the actual embeddable SmugMug subdomain URL: the requested wildcard CSP does not authorize a bare-apex frame unless it redirects to an authorized subdomain. External album privacy/embed policies still apply.
- `GET/PUT /api/admin/dues` (admin only) stores `dues: {seasonOpen:boolean,text:string}`; default is closed/empty. Changes are audited `dues-settings-edit` without copying payment instructions into the audit. `GET /api/dues` and `/dues` are signed-in only; the server withholds the text while closed. Text/links render safely without HTML injection. No payment processing, member-specific balance or payment integration is implemented in this stage.

## Working rules

- Confirm and state the database host before any reporting query; never write to production.
- Audit before fixing; verification names its method; label inferences; say when unfinished.
- Private data is withheld on the server, never merely hidden in the UI.
- Nothing is hard-deleted: retire/end instead (sign-out may remove its session).
- Audit log is append-only at the database level. Tests never touch real person records.
- Identity comes from the HWD Roster. Do not share the member list, cookie, or application database with the other HWD apps.
- Keep missing settings feature-local; development mail is console-only; production `APP_ORIGIN` must be explicit.
